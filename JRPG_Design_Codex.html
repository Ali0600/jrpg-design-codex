Reading the codex

Every mechanic is one card. The colored orb is its category — hover the legend below. Click a card to open it. The green Reward Loop panel is the heart of each entry: what the player does, what they get, and why it feels good. That's the part to study for your exploration-reward design.

The research pipeline

The Games tab is a research queue, not just a list. Games sort by status — Researching first, then To Research, then the finished shelf — and each card shows how many mechanics and minigames it has contributed so far, so coverage gaps are visible at a glance.

Every game has a page. Click a game's name anywhere — its card, a mechanic, a minigame — to open it: the cover, what its GameFAQs page says (platform, genre, developer, publisher, release, franchise, and how GameFAQs readers rate it, its difficulty and its length), every mechanic and minigame it contributed, its screenshots, its sources, the lineages it sits in, the codex games most related to it (a shared series, studio, director, composer or other credit, each shown as a link), and the games GameFAQs readers pair it with — those already in the codex link across, the rest can be queued for research with one click. The address carries the page (#game=…), so the browser's Back button returns to the list and a link can be shared. The list itself can be searched by title, developer, genre, franchise or platform, and sorted by the GameFAQs rating beside the Metacritic sorts.

Everything on a game is a filter. Click a platform, a genre, a developer, a publisher, a series, a theme, a feature, an award, a year or a name in its credits on a game's page to list every game that shares it (the platforms, credits, themes and awards come from the game's Wikipedia article as well as its GameFAQs page); click one on a card in the list to narrow the list you already have. The search box takes the same filters as words — platform:PC genre:"Action RPG", alongside ordinary text — and shows each one as a chip you can remove. Browse, under the search box, lists every value with the number of games carrying it. Sources spell one thing several ways, so each value is shown in one spelling: GameFAQs' Role-Playing is RPG, and SquareSoft, Squaresoft and Square are all Square. The address carries the filters, so Back returns to the page you came from and a filtered list can be shared. The Mechanics and Minigames searches take the same words, answered through each row's game (platform:SNES on Mechanics lists every mechanic from a SNES game), plus words about the row itself: cat:, verb:, want: (yes, maybe, no or undecided), game: and id: for mechanics, and table:yes or table:no (whether a minigame has a reward table), game: and id: for minigames. Those two searches are not kept in the address.

  1. Queue it. Add the game with status To Research, and write the "why" as a research brief: the specific question this game should answer (the queued cards marked BRIEF show the shape).
  2. Research it. Set it to Researching, then play it or work through deep dives and wikis with the codex open. Log mechanics with + Add mechanic as you notice them.
  3. Always fill the Reward Loop. If you can't describe the loop, you haven't understood the mechanic yet.
  4. Rewards must be concrete. "Prizes and gil" is not research — name the actual items and the thresholds that earn them. Minigame cards carry a reward table for exactly this.
  5. Rate it 1–5 and decide Yes / Maybe / No. For Yes and Maybe, write how it adapts to your game, stripped of the source game's specifics.
  6. When done, set the game to Researched. Periodically filter to Yes — that cluster is the seed of your game design document.

Turning research into a design

The My Game tab is where the codex stops being a library. Everything marked Yes collects there as a shortlist, and each one gets placed into a system of the game you're building — discovery, combat, progression, venues, world. Each system has its own notes box for the rules those mechanics have to serve.

Each shortlisted mechanic also carries the five design pillars as chips, I to V, and a none. Tick the pillars it really serves; hover a chip for that pillar's test question. The strip at the top counts how many mechanics serve each pillar and how many you have not judged yet, and each card on the Design Pillars tab carries the same count. A pillar with little behind it is the part of your design the shortlist does not support yet. Nothing here is worked out from a mechanic's category: the judgement is yours.

Each shortlisted mechanic also names the people behind its game: director, designer, writer and composer. Whose work you keep picking, just above the board, lists the names that recur across two or more of your shortlisted games. It is a taste profile, and a name links to every codex game that person worked on.

The value is in the placing. A mechanic you can't assign to a system is a mechanic you liked without knowing what it's for, and a system holding twelve entries is one you're overbuilding. Use Parked honestly — "worth loving, not worth building here" is a real answer, and a shortlist with nothing parked usually means nothing has been decided.

The UI Gallery

The UI Gallery tab holds real screenshots of the researched games' interfaces — battle HUDs, menu screens, minigames — filterable by game and by screen type, each captioned with what the UI is showing. Use it three ways: as reference when designing your own screens, to study how another game solved the same layout problem, and to check a codex claim against what's actually on screen. Thumbnails also appear on each game's card in the Games tab and on its page; the box art beside each game's name comes from covers/ (sources in covers/SOURCES.md), and a bare copy of the file without that folder shows the game's initials instead.

The images live in the shots/ folder beside this file (sources in shots/SOURCES.md). If you open the bare HTML without that folder, the gallery simply explains itself — nothing else breaks.

Your edits are saved

Ratings, decisions, notes, and new entries save automatically in this browser (when opened as a local file). They live in this browser only — use Export backup now and then to download a JSON snapshot, and Import backup to restore it or move to another computer. If your browser blocks local storage, the page still works for reading and filtering; just export before closing to keep changes.

Storage is per address. Opening the file from your disk and opening the hosted copy at ali0600.github.io/jrpg-design-codex are two separate stores — work done in one will not appear in the other. Export from the one you've been using and import into the other to bring your decisions across.
